# 用我的声音生成 TTS

## 固定配置

- CLI：`/opt/homebrew/bin/speech`
- 子命令/引擎：`speech speak --engine cosyvoice`
- 参考音频：`/Users/world/Library/Caches/audio.soniqo.studio/references/haoqin-25-52791d24.mp3`
- 参考音频文本（必须原样传入 `--cosy-reference-transcript`）：
  `今天的天气还不错，我准备出去走一走。最近我一直在尝试一些新的工具，希望能找到更简单、更高效的方法。对我来说，最重要的不是功能有多少，而是它能不能真正解决问题，用起来是不是足够自然。`
- 默认语言：`chinese`
- 默认输出：WAV，保存到 `~/Downloads/`

## 交互步骤

1. 从用户消息/提供的稿件中取得完整待合成文本。若文本尚未提供，先请用户提供。**不可在用户选定模式前开始合成。**
2. **每次生成前都必须主动显示完整的 A–E 菜单并询问用户选择；没有默认模式，不得因用户没选而自行决定，也不得跳过询问。** 即使用户已提供文本或提及风格，也先显示菜单，除非用户在本轮明确选择了菜单选项。

   固定菜单内容如下，必须直接展示 D 的名称和简短说明，不得把个人预设藏在 C/E 的子菜单里：

   - **A. 自然模式**：不添加 `--cosy-instruct`。
   - **B. AI 自动匹配**：根据全文内容自动决定合适的表达方式；保持自然、克制，不逐句频繁切换风格，避免 AI 配音腔。需要风格指令时使用 `--cosy-instruct`。
   - **C. 手动选择**：用户可输入英文原名或对应中文名称；两种写法映射到同一风格，最终将英文原名作为 `--cosy-instruct`：
     - `soft` — 轻柔
     - `warm` — 温暖
     - `whispering` — 耳语
     - `intense` — 强烈
     - `excited` — 兴奋
     - `happy` — 开心
     - `calm` — 平静
     - `serious` — 严肃
     - `surprised` — 惊讶
     - `sad` — 悲伤
     - `angry` — 愤怒
     - `dramatic` — 戏剧化
     - `laughs` — 带笑声
   - **D. 我的知识旁白**：个人预设——自然、平和、亲切、克制的讲述，正常语速，转折和重点轻微强调，不夸张、无明显 AI 配音腔。将下方固定完整要求原样作为 `--cosy-instruct` 传入：
     `自然、平和、亲切、克制地讲述，保持正常自然语速；根据内容的转折和重点做轻微强调，不夸张，不使用明显的 AI 配音腔，整体像本人自然地向观众讲解内容。`
   - **E. 自定义**：询问用户输入自然语言风格要求，并将其作为 `--cosy-instruct`。

   以后新增的个人预设也必须作为独立选项直接列在主菜单中，并显示名称与简短说明。
3. 只有用户明确选择 A–E（以及 C/E 所需风格）后才生成。若用户只提供文本而没有明确选择，显示完整菜单并等待选择。

## 生成前检查与安全

- 如 CLI 参数不确定，先执行 `/opt/homebrew/bin/speech speak --help` 核实，不猜参数。
- 确认 CLI、参考音频存在；只读检查，不修改参考音频或 Speech Studio。
- **禁止下载或安装模型，禁止更换/指定模型变体。** 不传 `--model-id`、`--cosyvoice-variant` 等模型选择参数。仅使用已缓存的默认 CosyVoice3 模型；如果不能确认所需模型已在本机缓存，或运行提示需要下载，停止并告知用户，不继续触发下载。
- 短文本、长文本、API 和 Bob 默认都不做 ASR。长文本按下文流程自动分段并持久保留每个 Block WAV、时间轴和 manifest，便于人工试听后只重生成问题块；中间与诊断文件只放入本次任务独立 records 目录，不改动参考音频、Speech Studio 或其他无关文件。
- 只使用现有模型缓存；运行若提示下载模型，立即停止，不触发下载。

## Markdown → 朗读用纯文本

当输入来源是 `.md` 文件时，先生成仅供本次朗读/分段使用的纯文本，再进行字符数判断、分段和 TTS；绝不把 Markdown 原文直接传给 speech CLI。仅去除格式标记，不改写正文内容或顺序，保留适合朗读的标点和段落边界：

- 若文件开头有 YAML Frontmatter（从开头 `---` 到下一个独占行 `---` 或 `...`），整块删除，不朗读。
- 删除独占行形式的 Markdown 分隔线（`---`、`***`，允许行首/行尾空格）。不要把正文里的普通破折号误删。
- 标题行去除开头的 `#` 至 `######` 标记及其后空格，保留标题文字；标题仍按原顺序保留，并与正文段落分隔。
- `**粗体**`、`__粗体__`、`*斜体*`、`_斜体_` 去掉包裹标记、保留其中文字。
- 图片语法 `![alt](URL)` 默认整项删除，不朗读 alt 或 URL；链接语法 `[文字](URL)` 只保留“文字”。
- fenced code block（以三反引号围栏或 `~~~` 围栏开始、对应围栏结束）默认整块删除，不朗读代码内容；围栏外普通正文照常保留。
- 保持原段落先后与句读；删除语法后清理纯空行堆叠，但不要把相邻自然段无故粘连。
- Markdown 清理后的朗读纯文本须先完成下文“TTS 朗读规范化”，规范化后的副本才是后续分段、字符数统计、续跑清单及 TTS 的文本来源。朗读用文本及分段文件只存放在本次任务临时目录；按既有成功/失败规则保留或清理。
- 调用 CLI 时必须通过参数数组/安全引用将完整朗读文本作为一个独立参数传入，不能拼接成 shell 命令。参数位置应在所有 CLI 选项之后；若朗读文本首字符是 `-`，先按 `speech speak --help` 核实参数终止符是否受支持，支持时用 `--` 隔开选项与文本。若不支持，改用不会改变朗读内容的安全参数传递方式（例如仅在参数开头添加一个换行作为前缀）。无论如何，正文中间的 `--`、`---` 必须作为文本内容传递，绝不可被 shell/CLI 当成选项，也不得删改正文来规避。

非 Markdown 输入不做 Markdown 转换，但同样在朗读副本中执行下文的十进制与百分比规范化。

## TTS 朗读规范化

在 Markdown 清理完成后、字符数判断和长文本分段之前，仅对待朗读副本进行十进制数字与百分比的中文口语化，防止小数点被当作句号或百分比意义丢失。不得改动原始 Markdown 文件、参考声音或 reference transcript。

- 只处理 ASCII 数字组成的 `数字.数字` 十进制形式，例如可用 `(?<![0-9.])([0-9]+)\.([0-9]+)(?![0-9.])` 定位候选；须先识别并保护 URL、邮箱、文件路径及多点版本号/IP 地址等非十进制结构，不在这些结构内部局部替换。
- 整数部分按中文数值读法转换（`0` → `零`，`1` → `一`，`25` → `二十五`）；小数点转换为 `点`；小数部分逐位转换（`88` → `八八`），保留小数尾部的零。不自行四舍五入或改变数值。
- 百分比须在普通小数替换前识别并整体转换，先保护 URL、邮箱、路径、IP/版本号等非数值结构（包括 URL 中的百分号编码）；只对明确的数值百分比执行，例如 `96.5%` → `百分之九十六点五`、`20%` → `百分之二十`。允许数值与 `%`/`％` 之间有空格。整数部分按中文数值读法、小数部分逐位读；不四舍五入，不改变符号或数值，不重复转换已有中文“百分之”形式。
- 禁止简单删除 `%` 或把它仅当作可忽略标点。无法明确解释的百分号、复杂范围或数值结构保留原样并记录规范化疑点，不擅自删除或改写；在完成报告中列为 REVIEW，供用户按需抽听，不因该疑点自动阻断。
- 除明确百分比转换外，数字外的单位、字母、标点和段落顺序原样保留。例：`1.7B` → `一点七B`，`0.5B` → `零点五B`，`0.88` → `零点八八`，`25.36` → `二十五点三六`。
- 不替换所有 `.`，独立整数仍不普遍转换（百分比中的整数除外）；普通英文句点、省略号及非十进制内容保持不变。
- 保存/记录规范化后的朗读副本，后续分段与断点恢复沿用该副本；不要对已有成功分段临时采用不同转换规则。本步骤不改变 A–E 模式及音频生成/合并策略。

## 长文本 TTS

### 何时分段及如何切分

- 待合成正文（Markdown 输入先转换为朗读用纯文本，再完成十进制与百分比朗读规范化；不含空白字符）超过 **1,200 个字符**时自动进入长文本流程；1,200 字及以内一次生成。模式仍严格遵循上面的 A–E 交互，同一任务只询问一次；没有用户选择不得开始合成。
- 长文本使用较小语义块，每次 TTS 调用目标为 **80–200 个非空白汉字/字符**，以约 **150 字符**为组合参考；语义完整优先，必要时允许略超。
- 优先按自然段组织；短段（不足约 80 字符）与相邻语义关联段合并。保持段落顺序、段间换行和原有句读。
- 组合时，在自然段边界选择接近 150 字符、通常不超过 200 字符的位置；标题与紧随其后的第一段优先同块。
- 长自然段仅按句号、问号、感叹号等完整句子边界拆分，绝不从句中硬切；单个超长句保持完整。
- 末尾不足 80 字符的余块优先与上一块合并或在完整句界重新平衡，避免极短尾块。
- 分块后检查顺序及内容覆盖：按原序连接各块的非空白内容应与规范化朗读副本一致，防止准备文本时遗漏或重复。

### 长文本默认流程：不使用 ASR

- **默认长文本流程不调用 ASR。** 不运行 Qwen3-ASR，不生成 ASR 转写、PASS / REVIEW / FAIL，也不让语音识别结果阻断生成。
- 生成流程固定为：**准备朗读文本 → 分块 → 逐块 TTS → 检查 WAV 文件有效 → 记录块时长 → 全部完成后生成时间轴 → 合并最终 WAV → 验证最终 WAV。**
- 每块只做音频文件级检查：命令成功、文件存在且非空、WAV 可读、能取得有效时长。若 CLI 执行失败、文件缺失/损坏或时长无效，立即停止并报告；不要自动下载模型，也不要跳过坏块继续合并。
- 短文本、API、Bob 与长文本均不做 ASR。不要因为文本较长、数字较多或包含英文缩写而自动启用 ASR。
- 不再维护 ASR 相关的 REVIEW、REVIEW-BLOCK、FAIL 状态。内容是否忠实由用户实际试听判断；Skill 的职责是让问题块可以快速定位、局部重生成并重新合并。
- 本方案优先简单、稳定和可维护；除非用户以后明确要求重新引入 ASR，否则不要自行增加识别器、二次转写、投票或自动语义判定。

### 块文件与 records 结构

- 长文本必须持久保留 `reading-text.txt` 和 `segments.json`，保存至 `~/Downloads/<任务名>-records/`。
- 每块使用稳定编号，不把绝对时间写死到唯一文件名中，因为任意前块重生成后，后续时间都会整体移动。
- 推荐结构：

```text
<任务名>-records/
├── reading-text.txt
├── segments.json
├── timeline.md
├── manifest.json
├── block-001/
│   ├── text.txt
│   ├── attempt-1-seed-42.wav
│   └── attempt-1.log
├── block-002/
│   ├── text.txt
│   ├── attempt-1-seed-42.wav
│   └── attempt-1.log
└── ...
```

- `segments.json` 至少记录 block 编号、完整朗读文本及顺序。
- `manifest.json` 至少记录任务 base seed、每块当前选用 attempt、实际 seed、WAV 路径、音频时长、生成耗时，以及当前最终 WAV 路径（如已生成）。
- 不覆盖旧 attempt。对同一块重生成时新增 `attempt-2-seed-43.wav`、`attempt-3-seed-44.wav` 等。新 attempt 在用户明确试听确认“正确”前只是待确认候选，不得更新 manifest 中该块的“当前选用 attempt”；manifest 应保留此前已确认的选用版本。
- 所有 block WAV 都必须保留，方便用户直接点开某一段试听，不要求用户每次都从头听整篇。

### seed 与局部重生成

- 长文本任务使用固定 `base_seed = 42`，首次生成每一块都显式使用 seed 42。
- **正常首轮不会因为 ASR 自动重试。**
- 当用户人工试听指出某一块有问题时，即视为已授权修复该块；不需要用户再额外说“重做”“重新生成”或“重新合并”。只重生成该块：
  - 第一次人工修复：seed 43。
  - 第二次人工修复：seed 44。
- 同一块每次重生成都保存为新的 attempt，不覆盖之前 WAV；文本、参考声音、语言和既定风格保持不变，除非用户明确要求修改。
- 如果 seed 44 后用户仍认为该块有问题，停止自动递增 seed，先询问用户下一步，不自行无限重试。
- 固定 seed 用于提高可复现性，不保证不同块语速完全一致。
- 断点恢复时沿用同一份 `reading-text.txt`、`segments.json` 和 manifest；已有有效块不重生成，只补未完成块。

### 时间轴 timeline.md

- 全部当前选用 block WAV 有效后，必须依据实际音频时长生成 `timeline.md`。
- 时间轴使用**最终合并音频中的累计位置**，必须把块间 **0.25 秒静音**计入后续块的起始时间。
- 每个 block 至少记录：
  - Block 编号。
  - 最终音频中的开始时间与结束时间，推荐 `MM:SS.mmm`；超过 1 小时时用 `HH:MM:SS.mmm`。
  - 当前选用 WAV 的相对或绝对路径。
  - 当前 attempt 与 seed。
  - 该块完整朗读文本，或清晰可识别的文本片段并同时指向 `text.txt`。
- 示例：

```text
Block 007
时间：03:22.480 - 03:57.910
Attempt：1
Seed：42
文件：block-007/attempt-1-seed-42.wav
文本：我现在更愿意把生成流程重新做简单……
```

- `timeline.md` 是用户定位问题的主要索引。用户可以直接说“最终音频 4:18 左右有问题”，Agent 必须先查 timeline，定位对应 block，再处理该 block；不要让用户自己计算。
- 用户也可以直接说“Block 009 有问题”，此时直接定位该块。
- 任意块被重生成并选用新 attempt 后，必须重新读取**所有当前选用块**的实际时长，重新计算完整 timeline；不能只改问题块那一行，因为后续时间可能整体变化。

### 人工试听修复流程

当用户指出最终音频某个时间点或某个 block 有问题时：

1. 读取本任务 `timeline.md`、`manifest.json` 和对应 `text.txt`，确定目标 block。
2. 用户说“4:18 左右读错了”“这里多读了”“Block 009 有问题”等，已经构成明确修复指令。定位到唯一 block 后直接进入局部修复；只有时间点落在边界、无法唯一定位，或用户明确要求“先别重做/先只定位”时才追问。
3. 只重新生成该 block，不重生成其他正常块。
4. 使用该块下一次 repair seed（第一次人工修复用 43，第二次用 44），保存为新的 attempt，绝不覆盖旧 WAV。
5. 检查新 WAV 文件有效并取得时长；将它作为待试听候选，告知用户 Block、attempt、seed 和 WAV 路径。**此时不得更新 manifest 的当前选用 attempt，不得重算 timeline，也不得重新合并或替换最终 WAV。**
6. 等待用户试听反馈。用户明确确认“正确”后，才将该 attempt 设为 manifest 当前选用版本，重新读取所有当前选用块的实际时长、重算完整 `timeline.md`，按当前选用版本重新合并到新的最终 WAV（不得覆盖旧最终 WAV），验证并报告结果。
7. 用户反馈“不正确”时，保留该候选 WAV，继续为同一 Block 使用下一个 seed 生成新的 attempt，再提供试听路径；manifest 当前选用版本仍保持不变。seed 44 仍不正确时停止并询问下一步，不再自动递增。
8. 如果用户明确表示“只生成/给我试听 Block，不合并”，只生成并提供新的 Block WAV；不更新当前选用 attempt、不重算 timeline、不合并。以后用户确认正确后再执行第 6 步。

- 人工指出的“读错、多读、漏读、不自然”等都只影响目标 block，不自动扩散到其他块。

### 合并与重新合并

- 本机已存在 `/opt/homebrew/bin/ffmpeg`，无需安装新依赖。
- 首轮全部 block 有效后，按原顺序仅使用 manifest 当前选用 WAV 合并；相邻分段间加入 **0.25 秒**短静音。
- 可先用 `anullsrc` 生成静音 WAV，再以 concat demuxer 按“音频段、静音段、音频段……”建立任务目录内清单，执行 `ffmpeg -f concat -safe 0 -i <清单> -c:a pcm_s16le <最终临时 WAV>`。
- 如输入参数格式不一致，使用 ffmpeg 显式统一为单声道、24 kHz、PCM signed 16-bit 后合并；不得仅拼接 WAV 文件字节。
- 首次最终输出使用 `~/Downloads/my-voice-tts-<唯一时间戳>.wav`，不得覆盖已有文件。
- 局部修复后重新合并时也不要覆盖此前最终 WAV；使用新的唯一文件名，例如 `my-voice-tts-<原任务时间戳>-r1.wav`、`-r2.wav`，并在 manifest 中更新“当前最终 WAV”。
- 合并完成后用 `afinfo` 验证可读性、时长、单声道/采样格式，并检查文件非空。
- 最终 WAV 验证后只可清理可重建的 concat 清单、静音等临时文件；`reading-text.txt`、`segments.json`、`timeline.md`、`manifest.json`、每块文本、每次 attempt WAV 和日志都持久保留。

### 长文本完成报告

首轮生成完成后简洁报告：

- 最终 WAV 路径。
- `reading-text.txt` 路径。
- `timeline.md` 路径。
- records 目录。
- 总块数、最终音频时长、A–E 模式与风格。
- TTS 累计 CLI `Time`、任务墙钟总耗时。

## 执行

- 默认文件名使用清晰、唯一的名称，例如 `~/Downloads/my-voice-tts-YYYYMMDD-HHMMSS.wav`；如用户明确指定路径/文件名则遵从。先确认目标不会覆盖已有文件；若冲突，换一个唯一名称。
- 通过参数数组或安全的 shell 引号传递完整文本、transcript、风格和路径；避免文本中的引号/特殊字符导致命令注入或参数拆分。
- 记录命令开始和结束的墙钟时间；总生成耗时从启动 `speech speak` 前至其退出后计算，报告秒数。
- 使用 `--verbose` 获取合成统计；成功后检查输出 WAV，并用 `/usr/bin/afinfo`（macOS）读取音频时长。报告 CLI 给出的 synthesis `Time`（实际生成耗时）和 `RTF`；同时报告命令总墙钟耗时。如 CLI 未给出相关统计，明确写“未提供”，不要猜算冒充 CLI 数据。
- 合成失败、缓存缺失、输出文件无效时如实说明，不声称成功；不得为了排障下载模型。
- 默认不运行任何 ASR 命令。

## 命令参数模板

基础参数：

```text
/opt/homebrew/bin/speech speak --engine cosyvoice \
  --voice-sample /Users/world/Library/Caches/audio.soniqo.studio/references/haoqin-25-52791d24.mp3 \
  --cosy-reference-transcript '<固定参考音频文本>' \
  --language chinese --verbose -o '<输出 WAV 路径>' '<待合成文本>'
```

B 模式根据全文判断是否需要风格指令；C、D、E 模式均添加 `--cosy-instruct '<风格指令>'`（D 使用固定完整预设原文，C 使用映射后的英文风格名）。A 模式禁止传该选项。长文本每段沿用同一任务的选项与风格策略，并在首次生成显式添加 `--seed 42`；人工确认某块需要局部重生成时，该块下一次使用 43，再下一次使用 44。实际执行前按 CLI help 确认参数，并确保引用/转义安全。

## 完成后反馈

2. 音频时长。
3. 实际生成耗时（CLI synthesis `Time`）及任务总耗时。
